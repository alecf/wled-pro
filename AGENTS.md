# WLED Pro

A modern UI for WLED LED controllers built with React, TypeScript, and Vite.

## Commands

This project uses [Bun](https://bun.sh) as its package manager and script runner (version pinned in `package.json` `packageManager`). Don't use npm/yarn/pnpm — the lockfile is `bun.lock`.

```bash
bun install             # Install dependencies
bun run dev             # Start dev server
bun run build           # Build for production (vite build + tsc typecheck)
bun run typecheck       # TypeScript typecheck only (needs src/routeTree.gen.ts, generated by vite)
bun run lint            # Biome lint + format check
bun run lint:fix        # Apply Biome fixes and formatting
bun run test            # Run tests (watch mode)
bun run test --run      # Run tests once
bun run test:coverage   # Run tests with coverage
bun run test:e2e        # Playwright e2e tests
bun run generate-icons  # Regenerate PWA icons from icon.svg
```

Before committing, run `bun run lint`, `bun run test --run`, and `bun run build`.

See [docs/testing.md](docs/testing.md) for the fake WLED device (Vitest via useFakeWled(), Playwright fixtures in e2e/support/, and `bun scripts/fake-wled.ts` for manual dev).

`CLAUDE.md` files in this repo just import the sibling `AGENTS.md`; edit `AGENTS.md`.

### Node version

Bun is only the package manager/script runner: `vite`, `vitest` and `playwright` run on Node. The supported range is `engines.node` in `package.json` (currently set by jsdom 30 / Vitest 5); CI pins Node via `actions/setup-node` in `.github/workflows/`. When a dependency upgrade raises its Node floor, update both.

### Build config (Vite 8 / Rolldown)

Use `build.rolldownOptions` (not `rollupOptions`) and `output.codeSplitting.groups` for vendor chunks (the `manualChunks` function is deprecated). After upgrading Vite, the PWA plugin or the router plugin, check `bun run build` still emits the `vendor-*` chunks and the `PWA ... precache` summary, and look for deprecation warnings in its output.

## Pull Request Workflow

**Keep AGENTS.md files up to date as part of every PR.** The root `AGENTS.md` and the per-directory ones (e.g. `src/hooks/AGENTS.md`, `src/components/common/AGENTS.md`) are the source of truth for how this codebase works:
- If a PR changes something these files describe (APIs, hooks, components, conventions, commands), update the matching `AGENTS.md` in the same PR.
- If feedback from code review (human or bot) or from a person would be useful guidance for future work, add it to the most specific `AGENTS.md` that applies, in the same PR that addresses the feedback. Examples: a convention to follow, a pitfall to avoid, a WLED API quirk.

**Review before opening (or updating) a PR.** Run `/code-review` on the branch's changes, and fix the obvious issues it finds, before you open or push to the PR. Mention anything you chose not to fix in the PR description.
- Do the review and the fixes in a fresh, unbiased subagent, not in the context that wrote the code. Don't fork the authoring context. Give it the branch, the diff range (e.g. `origin/main...HEAD`) and this file. Don't give it your own summary of what the change does or why it's correct.

### Key Patterns

**Controller Management**: Controllers are stored in localStorage and managed via the `useControllers` hook, which also holds the selected controller (`selectedUrl` / `selectController`). A controller's URL is its ID.

**WLED API**: The `WledApi` class in `src/api/wled.ts` wraps the WLED JSON API. Hooks in `src/hooks/useWled.ts` provide React Query integration with per-controller query keys.

**Query Keys**: All WLED query keys follow the pattern `['wled', baseUrl, resource]`. Use `getQueryKeys(baseUrl)` from `useQueryKeys.ts` to get type-safe keys:
```tsx
import { getQueryKeys } from '@/hooks/useQueryKeys'
const keys = getQueryKeys(baseUrl)
// keys.state, keys.presets, keys.effects, keys.palettes, etc.
```

**Real-time Sync**: When viewing a controller, the `_controller` layout route opens the app's only WebSocket (`ws://[host]/ws`) via `useWledWebSocket` and shares it through `ControllerContext`. Screens must read `state`, `info`, `queueUpdate`, etc. from `useControllerContext()` and never call `useWledWebSocket` themselves (WLED allows only ~4 WebSocket clients). WebSocket messages are written into the `stateInfo` query; HTTP polling fills the same query when the WebSocket can't be used (HTTPS page + HTTP controller) or is down. Home screen cards poll `/json/si` over HTTP (every 10s).

**Segment Operations Hook**: `useSegmentOperations({ initialSegments, onSegmentsChange })` holds the editor's local segments:
- `updateSegment(id, updates)`, `splitSegment(id, point)`, `mergeSegments(keepId, removeId)`
- `mergeGapUp/mergeGapDown(gapStart, gapStop)`, `convertGapToSegment(gapStart, gapStop)`, `setAllSegments(segments)`
- Operations read the latest segments from a ref, so rapid calls never see stale state. `initialSegments` is only read on mount.

**Light Show Editor**: `LightShowEditorScreen` mounts its editor once state (and, for presets, the presets list) has loaded. Preset edits start from the preset's stored segments. Live preview sends changes over the shared connection; Cancel (or live preview off) restores what the device showed when the editor opened. Save applies the segments and saves the preset in one `/json/state` request (`seg` + `psave` + `ib`/`sb`). Segment helpers live in `src/lib/segmentUtils.ts` (`toSegment`, `splitSegment`, `repairSegments`) and `src/lib/wled-state.ts` (`segmentsToDeviceUpdate`, which also deletes removed segments with `stop: 0`).

**Device config**: `/json/cfg` is fetched once (`keys.config`); `useWledFullConfig`, `useWledTimers`, `useNtpConfig` and `useLedHardwareConfig` select sections from it. Every config mutation invalidates `keys.config`.

**Playlists**: WLED stores playlists as presets with a `playlist` property. Save with `{psave, n, on, o: true, playlist}`; start by loading the preset (`{ps: id}`).

**PWA Support**: The app is installable as a Progressive Web App with offline support. The service worker caches app assets and provides runtime caching for fonts. PWA configuration is the `VitePWA` plugin in vite.config.ts.

**Safe Area Utilities**: Custom Tailwind utilities handle notched devices (iPhone X+, Android punch-holes):
- `pt-safe`, `pb-safe`, `pl-safe`, `pr-safe` - Basic padding with safe area insets
- `pb-safe-4` - Bottom padding + 1rem (for footers with content padding)
- `pb-safe-14` - Bottom padding + 3.5rem (for main content above tab bar)

Defined in `src/index.css` using `@utility` directives.

## Core Concepts & Vocabulary

### Controllers

Physical WLED devices that control LED strips. Each controller has:
- **URL**: IP address or hostname for API access; also the controller's ID
- **Name**: User-provided label
- **LED Count**: Total number of LEDs connected to the controller (from the device's info)

Controllers are stored in localStorage and managed via the `useControllers` hook.

### Segments (WLED Segments)

WLED's native feature for dividing an LED strip into zones with independent effects and colors. Each segment has:
- **ID**: 0-9 (WLED supports max 10 segments)
- **Range**: `start` (inclusive) and `stop` (exclusive) LED indices, e.g. start=0, stop=100 covers LEDs 0 through 99
- **Effect**: Animation pattern (Solid, Rainbow, etc.)
- **Colors**: Up to 3 color slots (usage depends on effect)
- **Palette**: Color gradient used by palette-based effects
- **Parameters**: Speed, intensity, and custom parameters (varies by effect)

**Important**: WLED segment `stop` is exclusive. Adjacent segments share an endpoint: [0, 200) and [200, 300) are adjacent with no gap or overlap. A segment covering the whole strip is [0, ledCount). The UI shows the last LED as `stop - 1`.

**Segment Repair**: When saving light shows, segments are automatically repaired to fix:
- Overlapping segments (truncates first segment to end before next)
- Out-of-bounds segments (truncates `stop` to ledCount)
- Zero-length or invalid segments (removed)

See `repairSegments()` in `src/lib/segmentUtils.ts`.

### Global Segments

App-specific feature for managing reusable LED zone layouts. Unlike WLED segments (which control effects), global segments are structural templates:
- **Per-controller**: Each controller has its own global segments
- **Named zones**: e.g., "Living Room", "Ceiling", "Accent"
- **Grouped**: Segments can be organized into collapsible groups
- **Persistent**: Stored on the controller at `/wled-pro-segments.json` (cached in memory while the app runs)
- **Reusable**: Can be applied to light shows to quickly split a single segment into multiple zones

Global segments are managed via `useSegmentDefinitions` hook and stored using the file-based storage system in `useSegmentFileSync`.

**Workflow**: Define your physical LED layout once using global segments, then apply them to any light show to instantly create matching WLED segments.

### Effects

Animation patterns that control how LEDs change over time. Each effect has:
- **ID**: Numeric identifier (0 = Solid, 1 = Blink, etc.)
- **Name**: Display name (e.g., "Rainbow", "Fire 2012")
- **Parameters**: Speed, intensity, and custom sliders/checkboxes
- **Color slots**: Which of the 3 color slots the effect actually uses (some use 0, 1, 2, or 3)
- **Palette support**: Whether the effect uses a palette gradient
- **Flags**: 1D/2D support, audio reactivity

Effect metadata is parsed from `/json/fxdata` and typed in `src/lib/effects.ts`. The app uses this metadata to show only relevant colors and display palette previews when appropriate.

### Palettes

Color gradients used by palette-based effects. Two types:
- **Built-in palettes** (IDs 0-70): Predefined gradients like "Rainbow", "Ocean", "Lava"
  - Stored as `[position, r, g, b]` tuples defining gradient stops
- **Custom palettes**: User-defined gradients
  - Can reference segment colors ("c1", "c2", "c3")

Palette metadata is fetched from `/json/palx` and rendered using the `PaletteColorStrip` component. `/json/palx` is paged: its `m` is the index of the _last_ page (pages `0..m`), not a page count, and out-of-range pages are clamped to `m`.

### Light Shows (Presets)

Saved configurations that capture the complete state of all segments. Stored on the WLED device at `/presets.json` (keyed by preset ID; playlists are presets too). Each preset includes:
- **Name**: User-provided label
- **Segments**: Array of segment configurations
- **Global settings**: Power state, brightness, transition time
- **Quick load label**: Optional 1-2 character shortcut

**Current State vs Presets**:
- **Current State**: The live, running configuration on the device
  - Editing current state applies changes immediately
  - Can be saved as a new preset
- **Presets**: Saved snapshots that can be loaded
  - Editing a preset starts from its stored segments; "Live Preview" (off by default) shows the edits on the device
  - Save overwrites the preset, Save As creates a new one; either way the device ends up showing the saved show

**Create New Light Show**: Resets to a single segment covering the entire LED strip with default orange color, ready for customization.

### Segment vs Global Segment - Key Differences

| Aspect      | WLED Segment                         | Global Segment                          |
| ----------- | ------------------------------------ | --------------------------------------- |
| Purpose     | Controls effect/colors               | Defines physical layout                 |
| Storage     | WLED device state                    | `/wled-pro-segments.json` on controller |
| Lifespan    | Part of current state or preset      | Persistent template                     |
| Properties  | Effect, colors, palette, speed, etc. | Just start, stop, name, group           |
| Count       | 0-10 per state/preset                | Unlimited per controller                |
| UI Location | Light Show Editor                    | Segments tab                            |
| Use Case    | "Make LEDs 0-50 rainbow"             | "LEDs 0-50 are the kitchen"             |

## PWA Features

WLED Pro is installable as a Progressive Web App:
- **Offline Support**: Service worker caches all app assets for offline access
- **Install Prompt**: Users can install the app on mobile and desktop
- **Auto-Updates**: Service worker automatically updates to new versions
- **App Icons**: Adaptive icons for all platforms (regular and maskable)
- **Theme Color**: Matches app branding (#0ea5e9)

### Customizing Icons

To customize the PWA icons:
1. Edit `public/icon.svg` with your design
2. Run `bun run generate-icons` to regenerate all icon sizes
3. Icons are generated in multiple sizes:
   - 192x192 and 512x512 (standard)
   - 192x192 and 512x512 (maskable for Android)
   - 180x180 (Apple touch icon)
   - 32x32 (favicon)

### PWA Configuration

PWA settings are in vite.config.ts using vite-plugin-pwa:
- **Workbox**: Precaches all static assets
- **Runtime Caching**: Caches Google Fonts
- **Dev Mode**: PWA works in development (devOptions.enabled: true)

### Quick Reference

**HTTP Endpoints**:
- `GET /json` - Full state (state + info + effects + palettes)
- `GET /json/si` - State + info only
- `GET /json/state` - Current state only
- `GET /json/info` - Device info
- `POST /json/state` - Update state

**WebSocket** (`ws://[host]/ws`):
- Receives state+info on connect and on any state change
- Send JSON state updates to control the device
- Send `{"v":true}` to request full state
- Max 4 concurrent connections per device

See https://kno.wled.ge/interfaces/json-api/ for upstream documentation.
